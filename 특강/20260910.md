# [TIL] PostgreSQL 함수(Function)와 프로시저(Procedure)를 활용한 트랜잭션 제어

## 📝 오늘 배운 내용 요약

- PostgreSQL에서 **Function과 Procedure**는 DB 내부에 복잡한 업무 로직을 작성하는 객체이며 반환값과 트랜잭션 제어 방식에 차이가 있다.
- Function은 작업 결과를 반환할 수 있어 **Supabase RPC**를 통해 외부 애플리케이션에서 직접 호출할 수 있다.
- 여러 단계의 INSERT와 UPDATE를 하나의 트랜잭션으로 묶어 오류 발생 시 전체 작업을 롤백함으로써 **원자성(Atomicity)**을 보장한다.
- 주문 당시의 상품명과 가격을 보존하기 위해 **가격 스냅샷**을 저장하며, 대용량 데이터는 Procedure의 `COMMIT` 제어를 통한 **배치(Batch) 처리**로 Lock 유지 시간을 줄인다.

## 1. Function과 Procedure 기본 개념

### PL/pgSQL의 역할

PostgreSQL에서는 `PL/pgSQL` 언어를 사용하여 변수 선언, 조건문(`IF`), 반복문(`LOOP`) 등의 복잡한 프로그래밍 로직을 DB 내부에서 직접 실행할 수 있다. 대표적인 객체로 Function과 Procedure가 있다.

### Function (사용자 정의 함수)

Function은 작업을 수행한 후 계산 결과나 상태값을 호출자에게 반환하는 DB 객체이다.

~~~sql
CREATE OR REPLACE FUNCTION get_discounted_price(
    p_original_price INT,
    p_discount_rate DECIMAL
)
RETURNS INT
LANGUAGE plpgsql
AS $$
DECLARE
    v_final_price INT;
BEGIN
    v_final_price := p_original_price
                     - (p_original_price * p_discount_rate);

    RETURN v_final_price;
END;
$$;
~~~

- `CREATE OR REPLACE FUNCTION`: 함수를 새로 생성하거나 기존 정의를 덮어쓴다.
- `RETURNS INT`: 함수가 실행을 마치고 반환할 데이터 타입을 정수형(`INT`)으로 지정한다.
- `DECLARE`: 로직 내부에서 사용할 변수 `v_final_price`를 선언한다.
- `RETURN`: 계산된 최종 결과값을 호출한 위치로 전달한다.
- 일반적으로 `SELECT get_discounted_price(10000, 0.1);` 형태로 조회하여 결과를 확인한다.

### Procedure (저장 프로시저)

Procedure는 일련의 작업을 수행하는 데 집중하는 DB 객체이며, 내부에서 `COMMIT`과 `ROLLBACK`을 사용하여 트랜잭션을 직접 제어할 수 있다.

~~~sql
CREATE OR REPLACE PROCEDURE reset_daily_stats()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE user_stats
    SET daily_visits = 0;

    COMMIT;
END;
$$;
~~~

- `CREATE OR REPLACE PROCEDURE`: 저장 프로시저를 생성하거나 덮어쓴다.
- `COMMIT`: 프로시저 실행 도중 변경 사항을 DB에 영구 반영하여 트랜잭션을 즉시 확정한다.
- 반환값을 전달하는 용도가 아니므로 `CALL reset_daily_stats();` 형태로 실행한다.

## 2. Function과 Supabase RPC

### Supabase RPC의 개념과 목적

Supabase에서는 PostgreSQL의 Function을 원격 호출할 수 있도록 **RPC(Remote Procedure Call)** 인터페이스를 지원한다. 복잡한 비즈니스 로직을 백엔드 서버나 DB 내부 함수에 위임하여 처리 속도를 높이고 데이터 정합성을 유지한다.

### Python 호출 코드

~~~python
response = supabase.rpc(
    "create_order_transaction",
    payload
).execute()
~~~

- `supabase.rpc()`는 호출할 PostgreSQL 함수 이름과 매개변수(`payload`)를 전달한다.
- `.execute()` 메서드를 명시적으로 호출해야 네트워크를 통해 DB로 실제 실행 요청이 전송된다.

### 반환 구조

Function은 JSON이나 객체 형태의 처리 결과를 클라이언트에 전달할 수 있다.

~~~json
{
    "success": true,
    "order_id": "주문 ID",
    "order_no": "주문 번호",
    "total_price": 175000
}
~~~

- 프론트엔드나 Python 애플리케이션은 DB 내부에서 복잡하게 처리된 트랜잭션의 성공 여부와 결과 요약값을 즉시 응답받는다.

## 3. 주문 트랜잭션과 원자성 보장

### 주문 처리에서 발생하는 유령 주문 문제

온라인 쇼핑몰 주문 시에는 여러 테이블에 연속적인 쓰기 작업이 일어난다.

~~~text
주문 생성 로직:
1. orders 테이블에 주문 메타데이터 저장
2. order_items 테이블에 구매 상품 목록 개별 저장
3. 각 상품 단가와 수량을 계산하여 총 결제 금액 산출
4. orders 테이블의 total_price 컬럼 업데이트
~~~

- `orders` 테이블 INSERT가 성공한 직후 네트워크 오류나 제약조건 위반으로 `order_items` INSERT가 실패하면, 주문 번호만 있고 주문한 상품은 존재하지 않는 **유령 주문 데이터**가 남게 된다.

### 트랜잭션과 원자성(Atomicity)

여러 작업을 논리적인 하나의 단위로 묶어 처리하는 방식을 **트랜잭션(Transaction)**이라 한다. 트랜잭션의 핵심 속성인 **원자성(Atomicity)**은 모든 작업이 전부 정상 반영(`COMMIT`)되거나, 중간에 하나라도 오류가 나면 지금까지의 모든 변경 사항을 작업 전 상태로 되돌리는 것(`ROLLBACK`)을 의미한다.

~~~text
[주문 트랜잭션 원자성 동작]

주문 생성 + 주문 상품 등록 + 총액 업데이트
             |
             +---> 전체 성공 시: COMMIT (모든 데이터 최종 저장)
             |
             +---> 중간 오류 발생 시: ROLLBACK (모든 변경 사항 취소)
~~~

- PostgreSQL Function 내부에서 예외(`EXCEPTION`)가 발생하면 해당 함수 내의 모든 변경 작업이 자동 롤백되므로 불완전한 주문 데이터가 DB에 남지 않는다.

## 4. 가격 스냅샷 설계와 JSONB 처리

### 가격 스냅샷(Snapshot)의 필요성

상품 테이블(`products`)의 가격은 수시로 변동될 수 있다. 주문 당시 상품 가격이 120,000원이었더라도 이후 관리자가 가격을 150,000원으로 인상할 수 있다. 이때 주문 상세 내역(`order_items`)이 `products` 테이블의 현재 가격을 단순 참조(JOIN)하도록 설계하면, 과거 주문의 영수증 금액까지 150,000원으로 변조되는 문제가 발생한다.

~~~text
[상품 테이블]                    [주문 상세 테이블]
products                         order_items
- name                           - item_name (주문 당시 상품명 복사)
- price                          - price     (주문 당시 단가 복사)
       ====== 주문 시점 복사 =====>
~~~

- 특정 시점의 데이터 상태를 복사하여 영구 보존하는 방식을 **스냅샷(Snapshot)**이라 한다.
- 클라이언트가 조작하여 보낸 결제 금액을 그대로 신뢰하지 않고, DB 내부 로직에서 `products`의 현재 기준 가격을 직접 읽어와 `order_items`에 스냅샷으로 저장해야 위변조를 막을 수 있다.

### JSONB 배열 파싱 처리

장바구니에 담긴 다수의 상품 데이터를 JSON 배열 형식으로 전달받았을 때, `jsonb_array_elements()` 함수를 사용하여 다중 레코드로 펼쳐 처리한다.

~~~sql
SELECT
    (elem->>'product_id')::UUID AS product_id,
    (elem->>'quantity')::INT AS quantity
FROM jsonb_array_elements(p_items) AS elem;
~~~

- `jsonb_array_elements()`는 JSON 배열의 원소들을 행(Row) 단위 데이터로 확장한다.
- `elem->>'속성명'` 연산자로 텍스트 값을 추출한 뒤, `::UUID` 및 `::INT` 타입 캐스팅을 적용하여 개별 상품의 주문 상세 등록 루프에 활용한다.

## 5. Procedure와 배치(Batch) 처리

### 대용량 트랜잭션과 DB Lock 문제

50,000건 이상의 대규모 데이터를 단일 UPDATE 문으로 한 번에 처리하면 트랜잭션이 종료될 때까지 오랜 시간이 소요된다.

~~~text
대용량 50,000건 단일 UPDATE 실행
             |
             v
긴 트랜잭션 시간 유지
             |
             v
해당 테이블 및 행에 배타적 잠금(Lock) 지속 유지
             |
             v
다른 사용자의 조회 및 수정 요청이 장시간 대기 상태에 빠짐
~~~

### 배치(Batch) 분할 처리

대용량 작업을 일정 크기(예: 5,000건)의 묶음 단위로 나누어 반복 수행하고, 각 단계마다 트랜잭션을 커밋하여 자원을 반환하는 방식을 **배치(Batch)**라 한다.

~~~text
전체 데이터 50,000건
    |
    +---> 5,000건 UPDATE 수행 -> COMMIT (Lock 해제)
    +---> 5,000건 UPDATE 수행 -> COMMIT (Lock 해제)
    +---> ... (반복 진행)
    +---> 10회 분할 작업 완료
~~~

- Procedure는 함수와 달리 루프 내부에서 직접 `COMMIT`을 실행할 수 있어 장기 잠금 발생 문제를 해결한다.

### LOOP 기반 배치 처리 프로시저 구조

~~~sql
LOOP
    -- 일정 개수의 데이터 분할 UPDATE/DELETE 처리

    GET DIAGNOSTICS v_rows_affected = ROW_COUNT;

    EXIT WHEN v_rows_affected = 0;

    COMMIT;
END LOOP;
~~~

- `LOOP ~ END LOOP`: 분할 작업 단위가 끝날 때까지 처리를 반복한다.
- `GET DIAGNOSTICS ... = ROW_COUNT`: 방금 실행된 쿼리로 실제로 영향받은 행의 개수를 파악한다.
- `EXIT WHEN v_rows_affected = 0`: 더 이상 수정할 대상 데이터가 없으면 반복문을 즉시 탈출한다.
- `COMMIT`: 해당 청크 작업 단위의 변경 사항을 DB에 영구 반영하고 잠금(Lock)을 해제한다.

## 6. 비교 정리

### Function과 Procedure 비교

| 구분 | Function | Procedure |
|---|---|---|
| 호출 방식 | `SELECT 함수명()` | `CALL 프로시저명()` |
| 반환값 | `RETURNS` 및 `RETURN` 구문으로 결과 반환 가능 | 일반적인 단일 반환값 없음 |
| 트랜잭션 제어 | 내부 `COMMIT` / `ROLLBACK` 명령 직접 실행 불가 | 내부에서 `COMMIT` 및 `ROLLBACK` 직접 제어 가능 |
| Supabase 연동 | `supabase.rpc()`를 통한 직접 호출 가능 | 직접 RPC 호출용으로 사용하지 않음 |
| 주요 활용 분야 | 주문, 결제, 데이터 정합성 보장, 수식 계산 | 대용량 데이터 마이그레이션, 주기적 배치 정리 |
| 핵심 설계 목적 | 작업 결과 반환과 전체 트랜잭션 원자성 유지 | 대량 작업을 묶음 단위로 분할하여 중간 커밋 수행 |

## 7. 전체 흐름 정리

### 주문 처리 트랜잭션 흐름 (Function)

~~~text
사용자 주문 요청 (API / RPC 호출)
    |
    v
Function 실행 (단일 트랜잭션 시작)
    |
    v
상품 유효성 검증 및 기준 단가 조회
    |
    v
orders 테이블에 주문 정보 등록
    |
    v
JSONB 배열 파싱 -> order_items 테이블에 단가 스냅샷 저장
    |
    v
총 주문 금액 계산 및 orders 테이블의 total_price 업데이트
    |
    +---> 정상 완료: 전체 작업 COMMIT 및 성공 결과 JSON 반환
    |
    +---> 중간 예외 발생: 전체 작업 ROLLBACK 및 오류 반환 (유령 주문 방지)
~~~

### 대용량 데이터 배치 처리 흐름 (Procedure)

~~~text
Procedure 호출 (CALL 실행)
    |
    v
LOOP 반복문 진입
    |
    v
지정된 크기(청크 단위)만큼의 데이터 UPDATE / DELETE 실행
    |
    v
영향받은 행 수(ROW_COUNT) 확인
    |
    +---> 처리 건수 = 0: 작업 완료로 판단하고 EXIT LOOP
    |
    +---> 처리 건수 > 0: COMMIT 실행 (트랜잭션 확정 및 Lock 해제) -> 다음 LOOP 반복
    |
    v
전체 대용량 데이터 배치 처리 완료
~~~

## 8. 핵심 정리

### 핵심 키워드 정리

- **Function**: 연산 결과값을 호출자에게 반환하며 단일 작업의 원자성을 보장하는 데 주로 사용하는 DB 객체이다.
- **Procedure**: 반환값 없이 DB 내부에서 명령을 일괄 실행하며 트랜잭션(`COMMIT`/`ROLLBACK`)을 직접 통제하는 DB 객체이다.
- **Supabase RPC**: 백엔드나 클라이언트에서 PostgreSQL Function을 원격 프로시저 호출 형태로 실행할 수 있게 돕는 기능이다.
- **원자성 (Atomicity)**: 여러 단계의 작업 묶음이 전부 실행되거나 전부 취소되어 일관성을 유지하는 트랜잭션의 기본 성질이다.
- **가격 스냅샷 (Snapshot)**: 상품 기준 정보의 변동에 영향받지 않도록 주문 시점의 상품명과 단가를 주문 상세 레코드에 복사해 두는 설계 기법이다.
- **배치 처리 (Batch Processing)**: 대규모 트랜잭션으로 인한 DB 잠금(Lock) 병목을 방지하기 위해 데이터를 일정 크기 단위로 나누어 순차 처리하고 커밋하는 방식이다.

## 9. 느낀 점

이번 특강을 통해 Function과 Procedure가 단순히 여러 SQL 문을 모아두는 저장 공간이 아니라, 반환값의 유무와 트랜잭션 제어 권한에 따라 사용 목적이 철저히 나뉜다는 점을 이해했다.
특히 주문 시스템처럼 다수의 테이블이 동시 갱신되어야 하는 작업에서는 Function을 활용하여 하나의 트랜잭션 단위로 묶어주어야 유령 주문과 같은 데이터 불일치 문제를 방지할 수 있음을 배웠다.
더불어 대량의 로그나 통계 데이터를 다룰 때는 무리한 단일 쿼리 대신 Procedure 내부의 `LOOP`와 `COMMIT`을 이용한 배치 분할 처리를 통해 DB 잠금(Lock) 유지 시간을 최소화해야 안정적인 서비스를 운영할 수 있다는 점을 정리할 수 있었다.
