## 1. LLM의 구조적 한계와 리스크

LLM(대규모 언어 모델)은 사전에 학습한 방대한 텍스트 데이터를 기반으로, 주어진 문맥 뒤에 올 가장 그럴듯한 다음 토큰을 확률적으로 예측하여 답변을 생성하는 인공지능이다.

- AI는 모든 사실을 완벽히 이해하고 답하는 것이 아니므로, 문장이 매끄럽고 자신감 있어 보여도 사실이 아닐 수 있다.
- LLM 활용 시 마주하는 대표적인 구조적 한계는 다음과 같다.
  - 사실과 다른 정보를 지어내는 환각 현상
  - 학습 시점 이후의 정보를 알지 못하는 지식 컷오프
  - 학습 데이터의 불균형으로 인한 편향성
  - AI를 맹신하여 발생하는 자동화 편향 및 과신
  - 장기적인 의존으로 인해 인간의 능력이 감퇴하는 디스킬링
- 따라서 AI 산출물을 그대로 적용하지 않고 사람이 직접 검증하는 과정이 필수적이다.

## 2. 환각 현상의 원인과 유형

### 2.1 환각(Hallucination)이란?

환각은 AI가 실제로 존재하지 않거나 사실과 다른 정보를 마치 사실인 것처럼 그럴듯하게 생성하는 현상이다. LLM은 답변의 사실 여부를 자체 검증하지 않고 확률에 따라 텍스트를 이어 나가기 때문에 발생한다.

### 2.2 발생 원인

~~~text
프롬프트 입력
    │
    ▼
문맥 분석 및 다음 토큰 확률 계산
    │
    ▼
확률적으로 토큰 생성 후 기존 문맥에 추가
    │
    ▼
위 과정을 반복하여 답변 완성
~~~

- LLM의 목표는 '사실 확인'이 아니라 '문맥상 가장 자연스러운 단어 연결'이다.
- 제공된 정보가 부족하거나 질문에 잘못된 전제가 포함되어 있으면, 빈 공백을 그럴듯한 거짓 정보로 채운다.

### 2.3 환각의 주요 유형

- **입력 충돌 환각:** 사용자가 제공한 프롬프트나 문서의 내용을 무시하거나 왜곡하여 답변하는 경우이다.
- **맥락 충돌 환각:** 긴 대화나 긴 문서 처리 중 앞서 언급한 내용과 뒤에서 생성한 내용이 서로 모순되는 경우이다.
- **사실 충돌 환각:** 현실 세계의 객관적인 사실, 역사적 사건, 데이터 등과 명백히 일치하지 않는 답변을 출력하는 경우이다.

### 2.4 환각 완화 방법

- 중요한 정보는 공식 문서나 원본 데이터를 통해 교차 검증한다.
- AI에게 출처를 명시하도록 요청하고 해당 출처의 실재 여부를 확인한다.
- 프롬프트에 "확실하지 않거나 모르는 내용은 추측하지 말고 모른다고 답하라"는 제약 조건을 설정한다.
- 최신 정보나 내부 데이터는 검색 및 외부 데이터베이스를 연계하여 제공한다.

## 3. 지식 컷오프와 데이터 편향성

### 3.1 지식 컷오프(Knowledge Cutoff)

지식 컷오프는 모델의 학습 데이터가 특정 시점까지만 수집되어 발생하는 한계이다.

- 학습 시점 이후에 발생한 법률 개정, 뉴스, 신제품 출시 등의 정보는 모델 자체 지식으로 답변할 수 없다.
- 최신성이 요구되는 작업에는 웹 검색 연계나 최신 자료 제공이 필요하다.

### 3.2 RAG를 통한 보완

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 모델 외부에 있는 최신 자료나 문서를 먼저 검색한 뒤, 그 내용을 AI에게 전달하여 답변을 작성하도록 유도하는 방식이다.

~~~text
사용자 질문 입력
    │
    ▼
관련 외부 자료/데이터베이스 검색
    │
    ▼
검색된 결과를 AI의 프롬프트 맥락으로 제공
    │
    ▼
제공된 자료를 바탕으로 신뢰도 높은 답변 생성
~~~

- 모델 자체의 지식 한계를 극복하고 최신 정보를 반영할 수 있다.
- 단, 검색된 원본 자료에 오류가 있다면 답변 역시 잘못될 수 있으므로 자료의 신뢰성 검증은 여전히 필요하다.

### 3.3 데이터 편향성(Data Bias)

AI는 학습용 데이터셋에 내포된 패턴과 가치관을 그대로 흡수한다.

- 데이터 내에 특정 성별, 인종, 직업, 문화에 대한 고정관념이나 불균형이 있다면 결과물에도 편향된 시각이 그대로 반영될 수 있다.
- AI의 결과물이 특정 집단에 불리하거나 차별적인 고정관념을 확대 재생산하지 않는지 지속적으로 점검해야 한다.

## 4. AI 과신과 인간 중심 제어(HITL)

### 4.1 자동화 편향과 과신

- **자동화 편향(Automation Bias):** 인간이 자신의 지식이나 직관보다 시스템 및 AI의 판단을 맹목적으로 더 신뢰하는 심리적 경향이다.
- **과신(Overreliance):** AI의 능력을 과대평가하여 검토 없이 출력물을 전적으로 수용하는 태도이다.
- AI의 유려한 문체와 자신감 있는 어조에 현혹되지 않고 비판적인 시각을 유지해야 한다.

### 4.2 디스킬링(Deskilling)

- 자동화 도구에 과도하게 의존하여 사용자가 기존에 보유하던 문제 해결 능력, 코딩 구현 능력, 비판적 사고력이 점차 감퇴하는 현상이다.
- AI가 작성한 코드를 단순히 복사하기보다 코드의 작동 원리와 로직을 직접 분석하고 점검하는 학습 태도가 중요하다.

### 4.3 Human-in-the-loop (HITL)

Human-in-the-loop는 인공지능이 모든 결정을 단독으로 내리지 않고, 주요 파이프라인에 인간의 검토와 승인 과정을 필수적으로 배치하는 설계 방식이다.

~~~text
AI의 초안 생성
    │
    ▼
인간의 결과 검토 및 팩트 체크
    │
    ▼
오류, 편향 및 비즈니스 규칙 수정
    │
    ▼
인간의 최종 승인
    │
    ▼
실제 환경 배포 및 업무 반영
~~~

- 의료, 법률, 금융, 인사 채용 등 오차가 중대한 리스크를 초래하는 분야에서는 반드시 인간이 최종 책임을 진다.

## 5. 주요 프롬프팅 기법 (Zero-shot, Few-shot, CoT)

### 5.1 Zero-shot 프롬프팅

별도의 예시 없이 지시문만 직접 전달하는 방식이다.

- 간단한 번역, 단순 요약, 기본적인 질의응답에 적합하다.
- 프롬프트 작성이 간편하지만, 복잡한 업무에서는 출력 형식이나 논리 전개를 엄격히 제어하기 어렵다.

~~~text
[Zero-shot 예시]
다음 문장을 자연스러운 영어로 번역해줘.
"오늘 날씨가 매우 화창하다."
~~~

### 5.2 Few-shot 프롬프팅

원하는 작업의 입출력 예시(Shot)를 1개 이상 제공하여 모델이 입출력 패턴과 형식을 학습하도록 유도하는 방식이다.

- 특정 분류 기준 적용, 정형화된 서식 유지, 일관된 스타일 유지가 필요할 때 효과적이다.

~~~text
[Few-shot 예시]
다음 예시를 참고하여 고객 리뷰의 감정을 분류해줘.

예시 1: 배송이 빠르고 안전하게 도착했습니다. -> 긍정
예시 2: 기대했던 것보다 품질이 많이 떨어집니다. -> 부정

입력: 제품은 마음에 드는데 배송이 다소 늦었습니다. -> 
~~~

### 5.3 Chain-of-Thought (CoT)

복잡한 문제를 곧바로 해결하게 하지 않고, 사고 과정을 여러 단계로 나누어 순차적으로 추론하도록 유도하는 프롬프팅 기법이다.

- 수학 계산, 다중 조건 논리 분석, 알고리즘 구현 등에 활용한다.
- **Zero-shot CoT:** 예시 없이 "문제를 단계별로 나누어 차근차근 생각해줘"와 같은 문구를 추가하여 단계적 추론을 유도한다.
- **Few-shot CoT:** 문제 풀이 단계와 추론 과정이 포함된 예시를 함께 제공하여 복잡한 문제를 해결하도록 유도한다.

## 6. RGC 프레임워크와 출력 형식 제어

### 6.1 RGC 프레임워크

RGC는 프롬프트의 품질과 일관성을 높이기 위해 요소를 구조화하는 프레임워크이다.

- **Role (역할):** AI가 취해야 할 전문적 페르소나를 지정한다. (예: "너는 10년 차 Python 백엔드 개발자이다.")
- **Goal (목표):** 달성해야 하는 구체적인 결과물을 명시한다. (예: "초급자를 위한 리스트 자료형 설명서를 작성한다.")
- **Context (맥락):** 작업 이해에 필요한 배경 정보를 제공한다. (예: "독자는 프로그래밍을 시작한 지 2주 된 학생이다.")
- **Constraint (제약 조건):** 준수해야 할 규칙이나 금지 사항을 정의한다. (예: "전문용어는 풀어서 설명하고, 예제 코드는 2개 이하로 제한한다.")

~~~text
[RGC 프롬프트 작성 예시]
- Role: 너는 IT 전문 교육 강사이다.
- Goal: Python의 리스트와 튜플의 차이점을 명확히 비교 설명한다.
- Context: 프로그래밍 기초 문법을 처음 배우는 초급자를 대상으로 한다.
- Constraint:
  1. 어려운 기술 용어는 쉬운 일상 단어로 대체한다.
  2. 실행 가능한 간단한 코드 예제를 포함한다.
  3. 마지막 부분에 핵심 차이점을 표 형태로 정리한다.
~~~

### 6.2 출력 형식 제어

결과물을 후속 작업이나 시스템에 연동하기 위해 형식을 엄격하게 통제한다.

- **Markdown:** 가독성이 높은 문서 구조화(제목, 목록, 인라인 강조 등)에 사용한다.
- **Table:** 비교 분석이나 정형화된 데이터 목록을 가독성 있게 표현할 때 활용한다.
- **JSON:** 프로그래밍 언어의 데이터 파이프라인이나 API 통신 규격에 맞추어 키-값 구조로 파싱할 때 사용한다.

~~~json
{
  "name": "홍길동",
  "role": "데이터 분석가",
  "status": "재직중"
}
~~~

## 7. 컨텍스트 엔지니어링

컨텍스트 엔지니어링은 단일 프롬프트 문장 작성을 넘어, AI가 최적의 결과를 산출할 수 있도록 참조할 전체 데이터 환경과 파이프라인을 체계적으로 설계하는 접근법이다.

- 단일 프롬프트 엔지니어링이 "어떻게 질문할 것인가"에 집중한다면, 컨텍스트 엔지니어링은 "AI에게 어떤 배경 문서, 데이터, 사용자 이력, 제약 규칙을 어떤 구조로 제공할 것인가"를 다룬다.
- 포함 요소: 시스템 프롬프트(역할/페르소나), 사용자 정보, 과거 대화 이력, 외부 참조 문서(RAG), 출력 규칙, 보안 가이드라인.

## 8. 비교 정리

### 8.1 프롬프팅 기법 비교

| 구분 | Zero-shot | Few-shot | Chain-of-Thought (CoT) |
|---|---|---|---|
| **예시 제공 여부** | 예시 없음 | 1개 이상의 예시 제공 | 추론 단계 예시 또는 단계별 사고 유도 |
| **프롬프트 복잡도** | 단순함 | 상대적으로 보통 | 상대적으로 보통 ~ 복잡함 |
| **주요 목적** | 빠른 질의 및 기본 작업 | 패턴 학습 및 출력 서식 제어 | 복잡한 논리 및 수학적 문제 해결 |
| **적합한 작업** | 일반 번역, 단순 텍스트 요약 | 텍스트 분류, 특정 톤앤매너 유지 | 다단계 계산, 논리 퍼즐, 코드 디버깅 |

### 8.2 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링

| 구분 | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|---|---|---|
| **관리 범위** | 단일 질의문 및 지시문 중심 | AI가 참조하는 전체 입력 환경 및 시스템 구조 |
| **핵심 활동** | 효과적인 지시 문장 및 키워드 작성 | 배경 데이터, 외부 검색(RAG), 사용자 이력 통합 |
| **목표** | 특정 요청에 대한 정확한 답변 유도 | 일관되고 신뢰도 높은 AI 작업 환경 구축 |

## 9. 전체 흐름 정리

LLM을 실무에 적용하여 안전하고 일관된 산출물을 얻는 전체 프로세스는 다음과 같다.

~~~text
[1. 작업 정의]
목표 설정 및 RGC 기반 요구사항 구조화
    │
    ▼
[2. 환경 설계 (컨텍스트 엔지니어링)]
역할 부여, 배경 데이터, 제약 조건, 출력 포맷(JSON/표) 확정
필요 시 최신 정보 보완을 위한 RAG 파이프라인 연결
    │
    ▼
[3. 프롬프팅 전략 선택]
단순 질의(Zero-shot) / 형식 유지(Few-shot) / 단계적 추론(CoT)
    │
    ▼
[4. 모델 추론]
확률적 토큰 예측 기반 텍스트 생성
    │
    ▼
[5. 검증 및 통제 (HITL & 리터러시)]
환각, 지식 컷오프 오차, 편향성 검토 및 인간 최종 승인
~~~

## 10. 핵심 정리

### 핵심 개념

- LLM은 다음 토큰을 확률적으로 예측하는 모델이므로, 사실과 다른 내용을 그럴듯하게 출력하는 환각(입력/맥락/사실 충돌)이 발생할 수 있다.
- AI의 지식 컷오프는 RAG와 검색으로 보완하고, 자동화 편향과 디스킬링은 Human-in-the-loop(HITL) 검증 체계로 방지해야 한다.
- 프롬프트 작성 시에는 RGC(역할, 목표, 맥락, 제약 조건)를 명확히 정의하고, 작업 성격에 따라 Few-shot과 CoT를 전략적으로 활용한다.

## 11. 느낀 점

생성형 AI가 논리적이고 자신감 있는 어조로 답변하더라도, 실제로는 확률적인 단어 연결에 불과하여 환각이나 데이터 편향이 언제든 발생할 수 있음을 깊이 인식했다. AI가 제공하는 결과물에 과도하게 의존하는 자동화 편향을 경계하고, 복잡한 문제일수록 CoT나 Few-shot 등의 기법을 적용해 결과의 일관성을 확보해야 함을 배웠다. 앞으로 프로그래밍과 데이터 분석 작업을 진행할 때는 AI를 전적으로 신뢰하기보다, RGC 기반으로 명확한 맥락을 설계하고 최종 결과는 사람이 직접 검증하고 승인하는 체계를 유지해야겠다고 느꼈다.
