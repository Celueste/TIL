# 1. 핵심 개념

## Rebase

### 무엇인가?
Rebase는 브랜치가 갈라져 나온 기준점(Base)을 다른 브랜치의 최신 커밋으로 변경하는 작업이다.

### 왜 사용하는가?
불필요한 병합 커밋 생성을 방지하고, 하나의 선으로 이어지는 깔끔한 Git 히스토리를 유지하기 위해 사용한다.

### 어떻게 작동하는가?
~~~text
Rebase 전
A <-- B <-- C <-- main
       \
        D <-- E <-- feature

Rebase 후
A <-- B <-- C <-- main
             \
              D' <-- E' <-- feature
~~~

- 두 브랜치의 공통 조상을 찾는다.
- 현재 브랜치에만 존재하는 커밋을 임시로 떼어낸다.
- 브랜치의 시작점을 대상 브랜치의 최신 커밋으로 이동시킨다.
- 떼어냈던 커밋을 새 시작점 위에 다시 차례대로 적용한다.
- 이때 커밋 내용이 같아도 새로운 커밋이 생성되므로 커밋 해시가 달라진다.

### 핵심 원칙
- 이미 원격 저장소에 Push되어 다른 사람과 공유 중인 커밋은 함부로 Rebase하지 않는다.
- 해시가 변경되어 팀원들의 로컬 저장소와 히스토리가 어긋나는 문제가 발생할 수 있다.
- 개인 작업용 기능 브랜치에서만 사용하고, `main`이나 `develop` 같은 공유 브랜치에서는 주의해야 한다.

## 원격 저장소 관리

- Local Repository는 개인 컴퓨터에 있는 저장소이고, Remote Repository는 서버나 네트워크에 존재하는 저장소이다.
- Upstream 브랜치는 로컬 브랜치가 기본적으로 연결되어 추적(Tracking)하는 원격 브랜치를 뜻한다.

## GitHub 협업 도구

- 저장소 기본 문서: `README.md`(소개), `LICENSE`(라이선스), `CONTRIBUTING.md`(기여 규칙), `.github/`(설정 파일 및 템플릿).
- 작업 추적 도구: `Issue`(작업 단위 관리), `Label`(유형 분류), `Milestone`(목표 및 기간별 그룹화), `Project Board`(칸반 형태의 작업 상태 관리).
- PR(Pull Request): 작업한 브랜치를 대상 브랜치에 반영해 달라고 요청하며 코드 리뷰를 진행하는 협업 창구이다.

## AI/ML 프로젝트 Git 관리 이슈

- 대용량 파일: 가중치 파일(`.pth`, `.h5`, `.bin`)이나 데이터셋은 용량이 커 일반 Git 저장소의 성능을 저하시킨다.
- Jupyter Notebook: `.ipynb` 파일은 실행 횟수, 셀 출력 결과, 이미지 등의 메타데이터가 JSON 형태로 함께 저장되므로 무의미한 변경 사항이 커지고 충돌이 잦아진다.
- 보안: OpenAI, AWS 등 외부 서비스의 API Key나 인증 토큰이 실수로 원격 저장소에 노출되면 비용 및 보안 사고로 직결된다.

# 2. 실습 및 코드

## 브랜치 재배치와 병합

~~~bash
git switch feature
git rebase main

git switch main
git merge feature
~~~

- `git switch feature`를 통해 작업 브랜치로 이동한다.
- `git rebase main`을 실행하여 `feature` 브랜치의 시작점을 `main`의 최신 커밋 뒤로 붙인다.
- 작업 완료 후 `main` 브랜치로 이동하여 Fast-forward 병합을 수행한다.

## 원격 저장소 설정 및 동기화

~~~bash
git remote add origin <원격저장소_URL>
git remote -v
git push -u origin main
git push
git pull
git branch -vv
git pull --rebase origin main
~~~

- `git remote add origin`으로 원격 저장소를 등록한다.
- `git remote -v`로 연결된 저장소 목록을 조회한다.
- `git push -u origin main`으로 추적 브랜치(Upstream)를 설정하며 처음 Push한다.
- 이후에는 브랜치 명시 없이 `git push`, `git pull`로 동기화가 가능하다.
- `git branch -vv`는 로컬 브랜치와 원격 브랜치의 추적 관계를 상세히 출력한다.
- `git pull --rebase origin main`은 원격의 최신 변경을 로컬 작업 아래에 두고 로컬 커밋을 재배치하여 불필요한 Merge commit을 없앤다.

## GitHub Flow 작업 흐름

~~~bash
git checkout main
git pull origin main
git checkout -b feature/user-auth

git add .
git commit -m "feat: 로그인 기능 구현 (#12)"
git push -u origin feature/user-auth
~~~

- `main` 브랜치를 최신 상태로 업데이트한 뒤 기능 브랜치를 생성한다.
- 커밋 메시지에 `#12`처럼 Issue 번호를 기록하면 관련 Issue와 즉시 연결된다.
- PR 본문에 `Closes #12`를 작성하면 해당 PR이 Merge될 때 연결된 Issue가 자동으로 닫힌다.

## Git LFS 설정

~~~bash
git lfs install
git lfs track "*.pth"
git lfs track "*.h5"
git lfs track "*.bin"

git add .gitattributes
git commit -m "chore: configure Git LFS for model files"
~~~

- `git lfs install`로 로컬 Git 환경에 LFS를 활성화한다.
- `git lfs track` 명령어로 LFS가 관리할 대용량 파일 확장자를 지정한다.
- 지정된 설정이 기록된 `.gitattributes` 파일을 커밋하여 원격 저장소와 추적 설정을 공유한다.
- 실제 대용량 파일은 별도 스토리지에 저장되고 Git에는 메타데이터 포인터만 남는다.

## nbstripout 설치 및 적용

~~~bash
pip install nbstripout
nbstripout --install
nbstripout --status
~~~

- `pip install nbstripout`으로 도구를 설치한다.
- `nbstripout --install` 명령어로 현재 Git 저장소의 필터로 등록한다.
- 커밋 시점에 Jupyter Notebook의 실행 카운트와 출력 데이터를 자동으로 제거하여 코드 diff를 단순하게 유지한다.

## API Key 보안 설정

~~~bash
echo ".env" >> .gitignore
echo "*.env" >> .gitignore

pip install pre-commit
pre-commit install
~~~

- `.env` 파일을 `.gitignore`에 등록하여 실제 비밀키가 커밋 대상에 포함되지 않도록 방지한다.
- `pre-commit install`로 훅을 등록하여 커밋 실행 직전에 Secret Scanner나 코드 포맷터가 자동으로 실행되도록 설정한다.

## 작업 임시 저장 (git stash)

~~~bash
git stash
git stash list
git stash pop
git stash apply
~~~

- `git stash`는 커밋되지 않은 현재 작업 변경 사항을 임시 스택에 저장하고 디렉터리를 깨끗한 상태로 되돌린다.
- `git stash list`로 임시 저장된 목록을 확인한다.
- `git stash pop`은 가장 최근의 저장 내용을 복원하면서 스택 목록에서 제거한다.
- `git stash apply`는 작업 내용을 복원하되 스택 목록에는 기록을 그대로 남겨둔다.

## 특정 커밋 반영 (git cherry-pick)

~~~bash
git log develop --oneline
git cherry-pick abc1234
~~~

- `git log develop --oneline`으로 가져오고자 하는 커밋의 해시를 조회한다.
- `git cherry-pick abc1234`를 실행하여 해당 커밋의 변경 내용만 현재 브랜치에 새로운 커밋으로 복제 적용한다.

## 유실 작업 복구 (git reflog)

~~~bash
git reflog
git checkout -b recover-branch HEAD@{1}
git reset --hard HEAD@{1}
~~~

- `git reflog`는 `HEAD`가 가리켰던 모든 커밋 변경 기록을 순서대로 출력한다.
- 실수로 삭제한 브랜치나 `reset --hard`로 사라진 커밋 위치를 찾은 뒤 새로운 브랜치를 생성하거나 재설정하여 복구할 수 있다.

## Git Tag와 Release

~~~bash
git tag v1.0.0
git tag -a v1.0.0 -m "Baseline model"
git push origin v1.0.0
~~~

- `git tag v1.0.0`은 현재 커밋에 가벼운 태그를 부여한다.
- `git tag -a`는 작성자 정보, 날짜, 메시지가 포함된 주석 태그(Annotated Tag)를 생성한다.
- `git push origin v1.0.0`으로 태그를 원격 저장소에 업로드하며, GitHub Release와 연동하여 버전별 배포 패키지 및 모델 결과를 관리한다.

# 3. 오류와 해결

## Conflict (충돌)

### 오류 내용
브랜치 병합 또는 Rebase 도중 같은 위치의 코드가 달라 충돌 마커가 파일에 표시되는 상태이다.

~~~text
<<<<<<< HEAD
현재 브랜치의 내용
=======
병합하려는 브랜치의 내용
>>>>>>> feature/login
~~~

### 오류 원인
- 서로 다른 브랜치에서 같은 파일의 동일한 영역을 서로 다르게 수정했다.
- 한쪽에서는 파일을 삭제하고 다른 쪽에서는 같은 파일을 수정한 경우 발생한다.
- Git이 어느 코드를 우선해야 할지 판단할 수 없기 때문에 사용자의 수동 조정을 요구한다.

### 해결 방법
충돌 마커(`<<<<<<<`, `=======`, `>>>>>>>`)를 포함하여 필요 없는 내용을 지우고 남겨둘 최종 코드만 작성한다.

~~~bash
git status
git add <충돌_파일>

# 일반 Merge 진행 시
git commit

# Rebase 진행 시
git rebase --continue
~~~

- `git status`로 충돌이 난 파일을 확인한다.
- 충돌 파일을 수정한 뒤 `git add`로 스테이징한다.
- Merge 충돌은 `git commit`으로 마무리한다.
- Rebase 충돌은 커밋이 아니라 `git rebase --continue`로 다음 커밋 적용을 진행한다.
- 상황에 따라 Rebase를 건너뛰려면 `git rebase --skip`, 작업을 취소하고 이전 상태로 돌아가려면 `git rebase --abort`나 `git merge --abort`를 사용한다.

### 기억할 점
- 충돌은 오류가 아니라 수동 병합이 필요한 정상적인 과정이다.
- 충돌 해결 후에는 반드시 충돌 구분 마커가 파일에 남아있지 않은지 확인하고 스테이징해야 한다.

# 4. 비교 정리

## Git 병합 방식 비교

| 구분 | Merge | Rebase |
|---|---|---|
| 히스토리 | 분기와 병합 기록이 그대로 보존된다 | 선형적으로 깔끔하게 정리된다 |
| 병합 커밋 | 일반적으로 병합 커밋이 생성된다 | 별도의 병합 커밋을 생성하지 않는다 |
| 커밋 해시 | 기존 커밋 해시가 유지된다 | 커밋이 새로 생성되어 해시가 변경된다 |
| 히스토리 재작성 | 히스토리를 재작성하지 않는다 | 기존 히스토리를 재작성한다 |
| 안전성 | 공유 브랜치에서 안전하다 | 공유 브랜치 적용 시 충돌 위험이 크다 |

## 원격 동기화 명령어 비교

| 명령어 | 데이터 이동 방향 | 동작 방식 |
|---|---|---|
| `git push` | 로컬에서 원격으로 | 로컬의 커밋을 원격 저장소에 업로드한다 |
| `git fetch` | 원격에서 로컬로 | 원격의 변경 사항만 다운로드하고 현재 브랜치에는 합치지 않는다 |
| `git pull` | 원격에서 로컬로 | 원격 변경 사항을 가져온 뒤 현재 브랜치에 자동으로 병합한다 |

## GitHub PR Merge 전략 비교

| 전략 | 히스토리 특징 | 권장 사용 상황 |
|---|---|---|
| Merge commit | 분기와 병합 흔적을 그대로 기록한다 | 브랜치 분기 맥락과 전체 작업 흐름을 온전히 보존할 때 |
| Squash and merge | 여러 커밋을 하나로 합쳐서 반영한다 | 작업 중 생성된 자잘한 WIP(Work In Progress) 커밋을 정리할 때 |
| Rebase and merge | 커밋들을 대상 브랜치 최신 커밋 뒤에 순서대로 붙인다 | 개별 커밋 의미를 살리면서 선형 히스토리를 유지할 때 |

## 워크플로우 비교

| 워크플로우 | 관리 브랜치 | 특징 |
|---|---|---|
| GitHub Flow | `main`, 기능 브랜치 | 단순한 브랜치 구조, 빠른 개발 및 배포 주기, 소규모 팀에 적합 |
| Git Flow | `main`, `develop`, `feature`, `release`, `hotfix` | 엄격한 단계별 릴리즈 주기, 대규모 프로젝트에 적합, 복잡도 높음 |
| Trunk-based | `main`(또는 `trunk`), 단기 기능 브랜치 | 짧은 주기(하루 이내)의 잦은 통합, 높은 자동화 테스트 및 CI/CD 환경 요구 |

## Rebase 충돌 명령어 비교

| 명령어 | 동작 설명 |
|---|---|
| `git rebase --continue` | 충돌 해결 및 `git add` 완료 후 다음 커밋 작업을 계속 진행한다 |
| `git rebase --skip` | 충돌이 발생한 현재 커밋 적용을 건너뛰고 다음 커밋으로 넘어간다 |
| `git rebase --abort` | 진행 중인 Rebase 작업을 전체 취소하고 시작 전 상태로 되돌린다 |

# 6. 핵심 정리

## 핵심 코드

~~~bash
# 선형 히스토리 pull
git pull --rebase origin main

# LFS 추적 확장자 지정
git lfs track "*.pth"

# 노트북 메타데이터 자동 제거 설치
nbstripout --install

# 미완성 작업 보관 및 복구
git stash
git stash pop

# 유실된 커밋 탐색
git reflog
~~~

- `git pull --rebase`는 원격의 커밋을 먼저 두고 로컬 커밋을 재배치한다.
- `git lfs track`으로 대용량 파일의 실물 대신 포인터를 Git에서 추적하게 만든다.
- `nbstripout`은 노트북 파일의 실행 결과 노이즈를 제거해 Git diff를 줄인다.
- `git stash`는 임시 백업과 복구를 지원한다.
- `git reflog`는 HEAD의 모든 발자취를 추적해 유실된 커밋 복구의 단서를 제공한다.

## 핵심 개념

- Rebase는 브랜치 기준점을 옮겨 선형 히스토리를 생성하지만 커밋 해시를 재작성하므로 공유 브랜치 사용을 피해야 한다.
- Conflict는 동일 라인 수정 시 Git이 판단을 유보한 상태이며, 충돌 마커 제거 후 스테이징하여 해결한다.
- GitHub Flow는 `main`과 기능 브랜치만 사용하는 단순한 구조로, PR과 코드 리뷰를 거쳐 빠르게 배포하는 방식이다.
- Branch Protection Rules를 설정하여 `main` 브랜치에 직접 Push하거나 리뷰 없이 Merge하는 실수를 사전에 차단한다.
- AI/ML 프로젝트에서는 모델 가중치는 Git LFS로 분리하고, 노트북은 nbstripout으로 정제하며, API Key는 `.gitignore`와 pre-commit으로 유출을 방지한다.

# 7. 느낀 점

히스토리를 깔끔하게 정리해 주는 Rebase의 장점과 커밋 해시 변경으로 인한 위험성을 함께 배우면서, 개인 브랜치와 여러 사람이 공유하는 브랜치에서 취해야 할 전략이 왜 다른지 정리할 수 있었다. 충돌(Conflict) 상황 역시 도구의 오류가 아니라 작업자 간의 차이를 안전하게 조율하도록 돕는 필수적인 과정임을 이해했다.
