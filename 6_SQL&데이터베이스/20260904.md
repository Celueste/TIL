# 1. 테이블 간 관계 유형

관계형 데이터베이스에서는 여러 테이블이 서로 연결되어 전체 데이터 구조를 형성한다.
관계의 유형은 한 테이블의 데이터 1건이 다른 테이블의 데이터 몇 건과 연결될 수 있는지를 기준으로 구분한다.

## 1:1 관계 (일대일)

한 테이블의 데이터 1건이 다른 테이블의 데이터 1건과만 연결되는 구조이다.

```text
members (회원 기본) 1 ─── 1 member_details (회원 상세)
```

- 한 명의 회원은 하나의 상세정보만 가진다.
- 하나의 상세정보는 오직 한 명의 회원에게만 속한다.
- 데이터 보안이나 관리 편의를 위해 테이블을 나눌 때 주로 사용한다.

## 1:N 관계 (일대다)

한 테이블의 데이터 1건이 다른 테이블의 여러 데이터와 연결되는 구조이다.
실무에서 가장 흔하게 마주하는 기본 형태이다.

```text
members (회원) 1 ─── N orders (주문)
```

- 한 명의 회원은 여러 번 주문을 생성할 수 있다.
- 반대로 하나의 주문은 오직 한 명의 회원에게만 속한다.
- 다른 대표 예시로는 게시글(1)과 댓글(N), 부서(1)와 직원(N), 카테고리(1)와 상품(N)이 있다.

## N:M 관계 (다대다)

양쪽 테이블의 데이터 1건이 서로 여러 개의 데이터와 연결될 수 있는 구조이다.

```text
학생 N ─── M 강의
```

- 한 명의 학생은 여러 강의를 수강할 수 있다.
- 하나의 강의에는 여러 학생이 수강자로 등록될 수 있다.

# 2. N:M 관계와 중간 테이블

## 중간 테이블(Junction Table)이 필요한 이유

관계형 데이터베이스는 N:M 관계를 테이블 사이에 직접 연결하여 저장하기 어렵다.
한쪽 테이블 컬럼에 여러 개의 값을 쉼표 등으로 묶어 넣으면 데이터가 복잡해지고 중복이 발생한다.
따라서 N:M 관계는 가운데에 **중간 테이블**을 두고 두 개의 1:N 관계로 분리하여 관리한다.

```text
[학생] 1 ─── N [수강] N ─── 1 [강의]
```

- 학생(1)과 수강(N)이 1:N 관계를 맺는다.
- 강의(1)와 수강(N)이 1:N 관계를 맺는다.
- 수강 테이블은 학생의 식별자(`student_id`)와 강의의 식별자(`course_id`)를 함께 저장하여 다대다 관계를 깔끔하게 해소한다.

# 3. ERD 기본 구성 요소

ERD(Entity Relationship Diagram)는 데이터베이스의 전체 테이블과 그들 사이의 관계를 시각적으로 나타낸 설계도이다.

## 엔티티 (Entity)

- 데이터베이스의 **테이블**에 해당한다.
- 관리해야 하는 실제 대상(회원, 주문 등)을 의미한다.

## 속성 (Attribute)

- 테이블을 구성하는 각 **컬럼(Column)**에 해당한다.
- 회원의 이름, 이메일, 가입일 등 세부적인 데이터 항목이다.

## 관계 (Relationship)

- 테이블과 테이블 사이에 맺어진 **연결선**을 의미한다.
- 외래키를 통해 어떤 규칙으로 연결되어 있는지 선으로 표현한다.

# 4. Crow's Foot 표기법과 ERD 읽기

## 까마귀발 표기법 기본 기호

ERD 선 끝에 붙는 기호는 데이터가 몇 개까지 연결될 수 있는지를 나타낸다.

| 기호 | 명칭 및 의미 |
|---|---|
| `\|` | 1개 |
| `O` | 0개 (선택적) |
| `<` | 여러 개 (다수, N) |
| `\|\|` | 정확히 1개 (필수 1개) |
| `O<` | 0개 이상 (0 또는 다수) |
| `\|<` | 1개 이상 (최소 1개 이상의 다수) |

## ERD 관계를 올바르게 읽는 법

관계선은 반드시 양쪽 방향으로 각각 확인해야 전체 관계를 정확하게 알 수 있다.

```text
회원 || ───── O< 주문
```

- 회원 기준: 회원 1명은 주문을 안 할 수도 있고 여러 번 할 수도 있으므로 0개 이상의 주문(`O<`)을 가진다.
- 주문 기준: 주문 1건은 반드시 등록된 회원 1명에 의해서만 발생하므로 정확히 1명의 회원(`||`)에 속한다.
- 종합 결과: 회원과 주문은 1:N 관계가 성립한다.

## 복잡한 ERD를 해석하는 순서

- 가장 많은 선이 연결된 **중심 테이블**을 먼저 찾아낸다.
- 중심 테이블을 기준으로 뻗어나가는 연결 테이블들을 하나씩 차례대로 따라간다.
- 선 끝에 위치한 Crow's Foot 기호를 확인하여 최소 및 최대 개수를 질문 형태로 확인한다.
- 최종적으로 해당 연결이 1:1, 1:N, N:M 중 어디에 해당하는지 정리한다.

# 5. 비교 정리

## 관계 유형별 특징 비교

| 관계 유형 | 대응 관계 | 연결 특징 | 대표 실무 예시 |
|---|---|---|---|
| 1:1 | 1개 대 1개 | 데이터 분리 및 보안 목적으로 활용 | 회원과 회원 상세정보 |
| 1:N | 1개 대 다수 | 실무에서 가장 보편적으로 쓰는 관계 | 회원과 주문, 게시글과 댓글 |
| N:M | 다수 대 다수 | 직접 연결이 불가능해 중간 테이블로 해소 | 학생과 강의 (수강 테이블 활용) |

# 6. 전체 흐름 정리

```text
엔티티 및 속성 도출 (테이블, 컬럼 설계)
          │
          │
관계 유형 정의 (1:1 / 1:N / N:M)
          │
          │
N:M 관계 발견 시 중간 테이블 도입 (두 개의 1:N으로 분리)
          │
          │
Crow's Foot 기호 부여 (필수, 선택, 다수 여부 표기)
          │
          │
완성된 ERD 기반 데이터베이스 구축
```

# 7. 핵심 정리

### 핵심 개념

- **관계 판별 기준**: 테이블 A의 행 1건이 테이블 B의 행 몇 건과 닿아 있는지를 양방향으로 따져서 결정한다.
- **1:N 구조의 특성**: 자식 레코드는 부모 레코드 오직 1건에만 속하지만, 부모 레코드는 여러 자식 레코드를 가질 수 있다.
- **N:M의 해결책**: 다대다 관계는 그대로 두지 않고 중간 테이블을 생성하여 1:N 두 개로 쪼개어 저장한다.
- **Crow's Foot 기호 확인**: 선 끝의 직선(`|`)은 1, 동그라미(`O`)는 0, 갈라진 발(`<`)은 다수를 나타낸다.

# 8. 느낀 점

테이블 간의 관계를 단순히 이름만 외우는 것이 아니라 한쪽 데이터 1건을 기준으로 상대방 테이블을 몇 건 가질 수 있는지 양방향으로 따져보는 기준을 세울 수 있었다.
특히 학생과 강의처럼 서로가 서로를 많이 가질 수 있는 N:M 다대다 관계는 데이터베이스에 그대로 넣으면 데이터가 엉키기 때문에, 중간 테이블을 두어 1:N 두 개로 풀어낸다는 해결 방식이 명쾌하게 와닿았다.
복잡해 보이는 ERD라도 가장 선이 많이 모여 있는 중심 테이블부터 차근차근 따라가고 까마귀발 기호를 하나씩 뜯어보면 전체 데이터베이스의 그림을 파악할 수 있다는 점을 배웠다.
